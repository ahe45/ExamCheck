## 작업 보관과 복구

- 업로드 미리보기는 30분, 시작한 작업과 결과는 24시간 보관한다. 등록 성공/실패 후 입력 임시 파일은 제거하고, 내보내기 결과 파일은 만료 시 제거한다.
- 파일 분석은 동시 1개(대기 8개), 최대 5분, 자식 프로세스 JavaScript 힙 512MiB 제한이다. 힙 제한은 프로세스 전체 RSS 제한과 다르다. ZIP은 최대 5,000항목, 총 해제 크기 500MiB, 개별 사진 20MiB 제한을 적용한다.
- 등록과 내보내기는 각각 동시 1개로 처리한다. 요청자는 본인 작업만 조회·다운로드할 수 있다. 등록 중 재전송은 같은 작업을 반환한다.
- 브라우저 새로고침 후 같은 탭의 sessionStorage를 통해 등록 결과를 다시 조회한다. 내보내기는 같은 조건으로 다운로드를 다시 누르면 이어 확인한다. 브라우저 종료·저장소 삭제까지 복구하는 사용자 작업함은 제공하지 않는다.
- 서버 재시작 때 PARSING/QUEUED/RUNNING 작업을 실패로 표시한다. 중간 등록은 DB 트랜잭션이 되돌리고 자동 재실행하지 않는다. 이미 성공한 작업은 성공 상태가 유지된다.
- 작업 실행기는 **API 인스턴스 1개** 기준이다. 여러 API 프로세스를 동시에 운영하려면 DB 작업 선점과 임대/heartbeat를 추가해야 한다.

## 검증 결과

- API 단위·HTTP 경계: 91개 파일, 606개 검사 통과.
- Web 단위·컴포넌트: 111개 파일, 449개 검사 통과 후 저장 직후 초안 갱신 회귀 검사를 추가해 관련 2개 파일 7개 검사도 통과했다(현재 Web 검사 총 450개). 로컬 실행은 `--maxWorkers=2`로 자원 경합을 제한했다.
- MariaDB 통합: 전체 19개 파일 73개 검사 통과 후, 출력 동시 재시도/만료 검사를 추가한 관련 2개 파일 13개 검사도 통과했다(현재 통합 검사 총 74개).
- Windows 설정·운영용 로그인 키: 5개 검사 통과.
- 코드 형식·lint·API/Web 및 통합 검사 타입 검사·운영 빌드 통과.
- 운영 빌드 재시작 후 health·로그인·30명 페이지 조회·양식 3개의 요약/상세 분리·정적 파일 gzip 전송을 확인했다.
- 브라우저: FHD 역할별 화면, 카드 줄바꿈 3개 해상도, 편집기·PDF, 대량 화면/업로드·내보내기 총 59개 시나리오를 검증했다. 전체 실행에서 57개 통과 후 블록 선택·스크롤과 기본 양식 의존성을 수정해 나머지 시나리오도 개별 재검증 통과했다. 저장 직후 초안 갱신 수정 후 관련 편집/저장/메뉴 이동 검사도 통과했다.
- 추가 업무 흐름: 업로드 오류·계정 변경·전형 설정·번호 유일 정책·순차부여/마감/인쇄 선택 5개 시나리오도 통과했다. 오래된 fixture의 필수 열과 현재 순차부여 화면 동작을 반영했다.
- 모든 대량·변경 검증은 격리한 임시 DB를 사용한다. 실제 운영 데이터에 합성 데이터를 넣지 않았다.

### 로컬 합성 데이터 측정

2026-09-19 마지막 대량/동시 처리 통합 검사 실행값이다. 로컬 MariaDB와 프로세스의 결과이며 서버 PC 실측이나 운영 응답 보장은 아니다. 처리시간은 다른 로컬 작업의 부하에 따라 달라질 수 있다.

| 데이터 규모 | 30행 페이지 조회 시간 | JSON 크기(압축 전) |
| ----------- | --------------------: | -----------------: |
| 10,000명    |                   7ms |       13,757 bytes |
| 30,000명    |                  15ms |       13,757 bytes |
| 50,000명    |                  27ms |       13,757 bytes |

5만 명 전체 JSON은 23,261,729 bytes였다. 동일 데이터의 30행 응답은 약 99.94% 작다. 이는 전송 대상 크기 비교이며 전체 작업 처리속도 향상률이 아니다. 전형·교시 조회 EXPLAIN은 `ix_candidate_operation` 인덱스와 `ref` 접근을 확인했다.

| 동시 부여 | 같은 전형 p95 | 서로 다른 전형 p95 | 중복 번호 |
| --------- | ------------: | -----------------: | --------: |
| 10개 요청 |          89ms |               10ms |         0 |
| 30개 요청 |       1,616ms |               27ms |         0 |

같은 번호 범위는 정확성을 위해 직렬 처리하므로 대기가 남는다. 서로 다른 전형의 병렬 처리는 유지된다. DB 엔진의 개별 잠금 대기를 별도로 측정한 수치는 아니다.

## 실행과 측정 방법

기존처럼 서버를 종료한 후 업데이트하고 `start-server.bat`을 실행한다. 의존성 준비, DB 마이그레이션(052~054 포함), 운영 빌드 후 서버를 시작한다. 검증 기준은 Node 22.15 이상/24와 MariaDB 11.4이다. 자연 정렬은 MariaDB의 NATURAL_SORT_KEY를 사용하므로 MySQL 호환을 검증한 것으로 간주하지 않는다.

기존 예제 JWT_SECRET을 그대로 사용하는 경우 운영 시작 시 무작위 로그인 서명 키를 한 번 생성해 .env에 저장한다. 사용자 지정 키와 계정 비밀번호는 유지한다. 키가 교체된 첫 실행 후에는 다시 로그인해야 한다.

선택적 측정은 .env의 `EXAMCHECK_PERFORMANCE_METRICS=1`로 켠다. SQL 본문·파라미터·개인정보는 기록하지 않는다. queryMs에는 DB 실행과 잠금 대기가 함께 포함되며 DB 엔진의 잠금 대기만 분리한 값은 아니다. 비동기 작업 전체 완료 시간은 최초 HTTP 요청 시간과 구분해야 한다. 기본값은 꺼짐이다.

재현 명령:

`npm run test:integration -w @examcheck/api -- performance candidate-jobs print-jobs`

`npm run test:e2e -- --project=performance-fhd --project=admin-card-layout --project=template-editor-fhd --project=fhd`

## 남아 있는 구조적 한계

- 운영 교시 명단 원본은 전체 조회한다. 화면 DOM만 가상화했으며 PDF 대상의 누락을 피한다. 서버 페이지/출력 스냅샷 분리는 추가 규모 측정이 필요할 때의 후속 항목이다.
- 최종 PDF 데이터 자체는 브라우저 메모리에 남는다. 이번 변경은 페이지별 사진·HTML·캔버스 중간 메모리를 제한한다. PDF 서버 분산 생성·중단 후 페이지 재개는 도입하지 않았다.
- XLSX 분석 결과의 텍스트 행 배열은 메모리에 적재한다. 사진 ZIP 바이너리 전체 적재는 제거했다. 이전 API 계약을 위한 호환 함수는 일부 남아 있지만 관리자 수험생 목록·업로드·내보내기 화면은 새 경로를 사용한다.
- 라벨 목록 전송량은 줄였지만 미리보기 메타데이터 생성 시 DB의 양식 JSON을 읽는다. 저장된 별도 썸네일 열/캐시는 추후 계측에 따라 검토한다.
- 시스템 설정 카드 조회는 요약으로 줄였지만 선택한 전형의 편집 화면에서 교시 구성을 만드는 기존 수험생 전체 조회는 남아 있다. 후속 개선 시 전형별 교시 집계 조회로 분리할 수 있다.
- 뒤쪽 OFFSET 페이지·대량 필터 선택지·장시간 읽기 스냅샷 비용은 데이터 증가에 따라 남는다. 커서 페이지와 별도 작업 서버는 필요한 규모가 확인될 때 도입한다.
- 실제 서버 PC의 네트워크·디스크·메모리, 실물 프린터와 대량 사진 PDF는 이번 로컬 자동 검증 범위 밖이다.
