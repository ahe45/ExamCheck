# ExamCheck 데이터 처리 성능 점검과 개선 제안

점검일: 2026-09-19. 소스 기준: `4d00af5`. **분석·제안 문서이며 운영 코드에 개선을 적용한 결과가 아니다.**

## 1. 범위와 결론

ExamList의 9월 18일 개선 커밋 `5a08e37`, `d476027`과 `doc/17-performance-review.md`를 참고했다. ExamCheck의 관리자 수험생 목록, XLSX·사진 ZIP 등록, 운영 명단·조회, 가번호 부여·마감, 라벨 출력, 문서 양식·PDF, 시스템 설정, 계정·인증, DB 연결·인덱스, 실행·검증 경로를 점검했다.

우선 개선 대상은 **불필요한 전체 데이터 이동, 업로드 중복 처리, 지나치게 넓거나 긴 잠금, PDF 반복 집계**다. ExamList의 목록·업로드 개선은 상당 부분 적용 가능하다. 반면 ExamCheck의 PDF는 브라우저에서 생성하므로 ExamList의 서버 PDF 병합 코드를 그대로 옮기는 것은 적합하지 않다.

확인된 비효율과 대규모에서 예상되는 병목을 구분했다. 로컬 DB는 수험생 100명, 사진 100건, 가번호 배정 2건, 출력 작업 14건, 문서 양식 3개로 작다. 이 상태에서 빠르다는 사실은 대규모 동시 운영 성능을 보장하지 않는다. 서버 PC 실측과 대량 부하 검증은 수행하지 않았다.

## 2. 실측 근거

실행 중인 로컬 개발 서버 `127.0.0.1:5173`를 경유해 API별 3회 요청했다. 응답 본문을 끝까지 읽은 시간이며 네트워크 환경이 다른 서버 PC와 비교할 수 없다. 업무 데이터 변경 없이 SELECT·EXPLAIN과 조회 API를 사용했다. 진단 로그인에 따른 정상 인증 감사 기록은 생성된다. 응답 원문·개인정보·인증 토큰은 보고서에 저장하지 않았다.

| 대상                       |  데이터 수 | 응답 본문 크기 | 3회 소요 시간         |
| -------------------------- | ---------: | -------------: | --------------------- |
| 관리자 수험생 목록         | 100명 전체 |   46,649 bytes | 7.1 / 5.7 / 5.8 ms    |
| 관리자 문서 양식 목록      |        3개 |  458,054 bytes | 19.5 / 12.7 / 14.9 ms |
| 사용자 문서 양식 선택 목록 |        3개 |  458,054 bytes | 12.2 / 11.1 / 11.5 ms |
| 운영 교시 목록             |       10개 |    2,091 bytes | 4.8 / 3.8 / 3.7 ms    |
| 대시보드 요약              |  집계 결과 |    2,012 bytes | 4.2 / 4.8 / 3.8 ms    |
| 한 교시 운영 명단          |       10명 |    7,177 bytes | 3.5 / 3.7 / 4.3 ms    |

모든 응답에서 `Accept-Encoding: gzip` 요청에도 `Content-Encoding`이 없었다. 양식 목록에서 `layout`만 제거하고 나머지 메타데이터를 동일하게 JSON으로 만들면 **637 bytes**다. 이것은 전송 계약을 분리했을 때의 크기 비교이며 새 API를 구현한 측정은 아니다. 편집·출력 시 선택한 양식 상세를 추가로 받아야 한다.

PDF 집계는 현재 소스의 `templateValues` 함수와 실제 `operationRowAttendance`를 이용해 합성 행으로 비교했다. 별도 진단 스크립트에서만 동일 그룹의 집계를 한 번 재사용하는 시제품을 실행했다.

| 합성 수험생 수 | 현재 집계·값 생성 | 집계 재사용 시제품 | 응시 판정 호출 수: 현재 → 시제품 |
| -------------- | ----------------: | -----------------: | -------------------------------: |
| 100명          |           16.9 ms |             4.4 ms |                     20,100 → 200 |
| 1,000명        |           67.3 ms |            45.4 ms |                2,001,000 → 2,000 |
| 3,000명        |          322.1 ms |           139.0 ms |               18,003,000 → 6,000 |

전체·응시·결시 인원과 개별 응시 판정이 모두 일치했다. 시간은 단일 로컬 대표 실행으로 JIT·실행 순서의 영향을 받는다. 이 비교는 **사진 다운로드, 그룹 찾기, HTML 생성, 캔버스 렌더링, PDF 저장을 제외**한다. 전체 PDF 속도가 같은 비율로 향상된다고 해석하면 안 된다.

## 3. 우선순위와 구현 제안

P1은 데이터 증가 또는 여러 단말의 동시 처리에 직접 영향을 주는 우선 개선, P2는 이후 단계의 개선이다. 우선순위는 장애가 이미 발생했다는 뜻이 아니다.

### P1-1. 관리자 수험생 목록을 서버 페이지 조회로 전환

- 근거: `apps/api/src/candidates/candidates.repository.ts:50`은 필터·LIMIT 없이 모든 행과 필드를 반환한다. `apps/web/src/features/candidates/CandidateDataPage.tsx:23`에서 전체를 받아 `apps/web/src/shared/hooks/useClientDataGrid.ts:47`에서 필터·정렬 후 30행씩 잘라 보여준다. 30행 표시가 30행 조회를 의미하지 않는다.
- 개선: `page/pageSize/sort/filters`를 검증하는 조회 계약을 만들고 현재 페이지·전체 건수만 반환한다. 동률 정렬에는 `id`를 추가해 페이지 중복·누락을 막는다. SQL 열 이름은 허용 목록으로 고정한다.
- 필터 선택지는 전체 권한 범위를 기준으로 별도 조회하고 조건별로 재사용한다. 현재 페이지만으로 선택지를 만들지 않는다. 빠른 조건 변경 시 요청 취소와 오래된 응답 무시를 적용한다.
- 관리자 수험생 다운로드는 현재 화면 필터를 전달하지 않는 별도 전체 다운로드다. 화면 필터와 다운로드 결과를 맞추려면 API·UI 계약을 함께 변경해야 한다. 운영 명단 다운로드에는 이미 필터 전달이 구현돼 있어 구분해야 한다.
- 검증: 1만·3만·5만 명에서 첫 페이지 바이트 수, DB 처리 시간, 필터 선택지, 페이지 간 중복, 정렬과 엑셀 행 순서를 비교한다. OFFSET의 뒤쪽 페이지가 실제로 느릴 때 커서 방식을 추가 검토한다.

### P1-2. 양식 목록과 상세 분리

- 근거: `apps/api/src/form-templates/form-templates.repository.ts:39`의 공통 SELECT가 목록에도 `layout_json` 전체를 포함한다. 인쇄 선택창은 `apps/web/src/features/candidate/useOperationPrint.ts:88` 부근에서 창을 열 때마다 활성 양식 전체를 받는다. 저장 후에도 `TemplateEditorWorkspace.tsx:157`에서 전체 목록을 재조회한다.
- 현재 카드 썸네일은 `TemplateLibrary.tsx`의 정적인 종이 모양이므로 실제 편집 내용 전체가 필요하지 않다. ExamList의 실제 썸네일 캐시를 먼저 이식할 이유가 없다.
- 개선: 목록은 코드·이름·설명·분류·범위·활성 상태·수정 버전만 반환하고 편집·출력·복사 시 해당 양식 상세만 가져온다. 비활성 양식도 관리자가 편집할 수 있도록 관리자용 상세 조회를 따로 제공한다.
- 저장 응답으로 변경한 카드와 상세 캐시만 교체한다. 데이터 태그 목록도 사용자 세션·카탈로그 버전에 맞춰 재사용한다. 라벨 양식의 목록/상세도 같은 원칙으로 분리한다.
- 효과 근거: 현재 문서 3개의 목록은 458,054 → 메타데이터만 637 bytes. 선택한 상세 조회 비용은 별도다.

### P1-3. XLSX·ZIP을 미리보기와 등록 때 두 번 보내고 분석하는 구조 제거

- 근거: `apps/api/src/candidates/candidates.service.ts:100,123,145,174`에서 미리보기와 등록이 각각 XLSX 파싱 또는 ZIP 해제를 한다. `CandidateUploadModal.tsx`도 등록 시 같은 파일을 다시 보낸다. 현재 preview token은 파일·DB 상태의 서명이며 분석 결과 저장소가 아니다.
- 개선: 최초 업로드를 임시 파일로 받고 파일 해시·사용자·종류·만료 시간을 포함한 업로드 세션을 만든다. XLSX 분석 결과를 제한된 수명으로 재사용하고 최종 등록은 세션 ID와 처리 정책만 전송한다.
- ZIP은 파일 목록과 크기 등 메타데이터를 먼저 읽고 실제 등록 대상 사진만 제한된 동시성으로 해제한다. 미리보기에서 이미지 유효성까지 보장해야 하는 현재 의미를 유지하려면 해당 검증도 제한된 메모리로 수행하고 결과를 재사용한다. 메타데이터 확인만 하고 기존 검증을 끝냈다고 표시해서는 안 된다.
- 현재 사진 제한은 업로드 200 MiB, 압축 해제 합계 500 MiB다. 메모리 업로드 버퍼와 모든 사진 content를 함께 보관할 수 있는 구조이며, 복수 요청 시 메모리 사용량이 누적된다. 상한이 있다고 저메모리 처리인 것은 아니다.
- 등록 시 현재 DB와 다시 대조하고, 미리보기 이후 충돌은 기존 정책에 맞게 재확인시킨다. 세션 재사용은 DB 검증 생략이 아니다. 성공·만료·연결 중단 때 임시 파일 정리와 다른 사용자 접근 차단이 필요하다.

### P1-4. 대량 등록의 전체 행 잠금과 한 행씩 저장 축소

- 근거: `candidates.application.ts:49` 이후 전체 기존 수험생을 `FOR UPDATE`로 읽고, 87행의 반복문에서 INSERT/UPDATE를 한 건씩 기다린다. 사진도 124행에서 모든 수험생·사진 참조를 잠근 뒤 134행 이후 개별 BLOB UPSERT를 수행한다. XLSX 등록은 전역 `system_profile` 행도 잠근다.
- 개선: 업로드 대상 키·수험번호에 필요한 기존 행과 버전만 조회한다. 시스템 전체 수험번호 유일성·동일인 일관성은 별도 최소 컬럼 조회 및 충돌 방지 장치로 유지한다. 전체 상태 해시를 대상/범위 버전으로 바꾸는 것은 비교 계약 변경이므로 별도 설계·검증한다.
- 변경된 행만 우선 100~200행 단위로 묶어 저장한다. 사진은 행 수뿐 아니라 BLOB 합계 바이트와 `max_allowed_packet`도 기준으로 나눈다. 200장 고정 묶음을 그대로 적용하지 않는다.
- 파일 분석·사진 검증·등록 계획은 가능한 한 트랜잭션 밖에서 준비하고, 최종 잠금 후 정책·충돌을 재검증한다. 한 트랜잭션 안에서 배치 SQL로 처리하면 기존 전체 성공/실패 의미를 유지하면서 DB 왕복 횟수를 줄일 수 있다. 무작정 조각별 COMMIT하거나 같은 연결에 Promise.all을 적용하지 않는다.
- 검증: 등록 실패 시 전체 롤백, 기존 행 ID·배정·사진 참조 유지, 마감된 범위 보호, 등록 중 현장 가번호 부여 지연과 교착 상태를 확인한다.

### P1-5. 가번호 부여·마감의 전역 직렬 처리 완화

- 근거: `pseudonyms.application.ts:224,430`에서 부여·마감이 모두 `loadPseudonymNumberPolicyForUpdate`를 호출한다. `pseudonyms.repository.ts:945`는 `system_profile WHERE id=1 FOR UPDATE`다. 다른 전형도 같은 행의 배타 잠금을 얻어야 한다. 부여 예정 번호 조회도 같은 경로로 진입한 후 롤백한다.
- 번호 한 건을 결정할 때 `loadReservedNumbers`로 해당 유일성 범위의 배정·사전 번호 목록을 다시 받는다. 같은 전형의 수험생 수가 커질수록 반복 비용이 늘어난다.
- 마감에서는 459행 이후 결시자를 한 명씩 저장하고 순차 번호 탐색도 범위 시작부터 반복한다. 동일 범위의 많은 결시자를 처리하면 이미 소비한 번호를 다시 검사한다.
- 개선: 정책 읽기와 번호 예약 잠금을 구분한다. 정책 변경은 배타적으로 보호하고, 일반 부여는 정책 공유 잠금 또는 명시적인 정책 버전 검증과 실제 유일성 범위의 잠금을 사용하도록 설계한다. ADMISSION 정책이면 전형 범위, SCHEDULE 정책이면 전형·교시 범위를 지켜야 한다. 단순히 FOR UPDATE를 제거하면 안 된다.
- 수동·사전 번호는 해당 번호의 점유 여부 중심으로 조회하고, 순차·추첨은 범위 커서/예약 상태를 활용한다. 마감은 범위별 다음 탐색 위치를 유지하고 배정 INSERT를 묶는다. 기존 재시도 멱등성·UNIQUE 제약·마감 원자성을 보존한다.
- 검증: 10~30단말에서 같은 범위/다른 범위를 구분해 p95 지연과 잠금 대기를 측정한다. 중복 번호 0건, 정책 변경과 동시 부여, 번호 소진, 앞자리 0, 마감·재개·재전송을 검증한다.

### P1-6. 라벨 이미지 생성 중 DB 잠금 유지 시간 단축

- 근거: `print-jobs.service.ts:45`에서 트랜잭션을 연 뒤 전형 설정과 수험생 등을 잠그고, 130행에서 `renderLabelPayload`를 기다린 후 commit한다. 한글 텍스트는 `label-payload-renderer.ts:39`에서 Sharp 이미지 변환을 거친다. 같은 전형의 설정 행을 잠그므로 여러 출력 단말의 작업 준비가 직렬화될 수 있다.
- 추가 비용: `print-jobs.repository.ts:203` 이후 라벨 한 장의 수험생 조회에 고사실 집계 3개를 항상 계산한다. 양식이 집계 태그를 쓰는지와 관계없다.
- 개선: 고정 한글 문구의 렌더링을 내용·폰트·크기·DPI 기준으로 제한된 캐시에 재사용하고, 집계는 실제 사용하는 경우 한 번의 조건부 집계로 계산한다. 요소별 무제한 Promise.all 대신 변환 동시성 상한을 둔다.
- 더 큰 변경은 짧은 트랜잭션으로 작업을 예약한 뒤 밖에서 렌더링하고 READY로 확정하는 구조다. 중간 상태·실패·만료·같은 수험생의 동시 작업 방지를 함께 구현해야 한다. 렌더링만 밖으로 옮겨 재출력 방지를 느슨하게 만들지 않는다.

### P1-7. PDF의 반복 집계와 전체 메모리 보관 줄이기

- 근거: `operation-template-pages.ts:47`은 매 행마다 소속 그룹을 다시 찾는다. 141~142행은 같은 그룹을 응시·결시로 각각 필터링한다. 수험생별 또는 수험생 그리드 양식에서 반복돼 한 그룹 N명일 때 집계만 O(N²)가 된다. 시간 포맷터도 행마다 새로 만든다.
- 개선: 작업 시작 시 전체 원본 명단으로 그룹·통계를 한 번 만들고 행→그룹 Map으로 접근한다. 출력 대상이 ‘응시만’이어도 기존처럼 원래 고사실 총원을 유지한다. 출력 시각과 포맷터도 작업당 한 번 고정한다.
- `buildOperationTemplatePages`는 사진 data URL을 포함한 모든 HTML을 만든 뒤 `template-renderer.ts:141`부터 페이지별 캔버스/PDF 생성으로 넘어간다. 사진 요청 동시성은 이미 4개로 제한돼 있지만 완료된 전체 결과 보관량까지 제한하지는 않는다.
- 다음 단계: 페이지/소규모 묶음 단위로 사진 준비→HTML→PDF 추가→참조 해제를 연결한다. 최종 PDF 자체의 메모리는 여전히 필요하다. 원본 사진 대신 인쇄에 충분한 크기의 이미지를 사용하는 것도 검토한다.
- DOM이 필요한 html2canvas를 그대로 Web Worker로 옮길 수는 없다. 대량 PDF 작업 재개가 필요한 경우에만 서버의 별도 브라우저 작업 프로세스를 검토한다. 현장 PC 작업을 모두 서버로 몰면 서버 병목이 새로 생긴다.

### P2-1. 교시 명단 조회와 화면 렌더링 분리

- 근거: `examinees.repository.ts:44`는 교시 전체 명단을 반환한다. `PseudonymAssignmentPage.tsx:116`은 `initialPageSize: 0`, 464행은 전체 필터 결과를 표시한다. 교시 인원만큼 DOM 행과 필터 계산량이 증가한다.
- 개선: 우선 화면에 보이는 행만 렌더링하는 가상 목록을 적용한다. 교시 데이터가 더 커지면 서버 페이지 조회+별도 전체 통계/필터 선택지로 전환한다. 조회·스캔·부여 응답은 해당 행에 반영한다. 이미 구현된 한 행 갱신은 유지한다.
- PDF가 현재 브라우저의 전체 명단에 의존하므로 그리드만 페이지 조회로 바꾸면 출력 대상이 누락된다. 출력 전용 전체 조회 또는 서버 작업용 스냅샷을 별도로 설계해야 한다.
- 여러 단말 동기화가 필요하면 버전 기반 변경 조회 또는 범위별 이벤트를 검토한다. 짧은 주기로 전체 명단을 다시 받아 해결하지 않는다.

### P2-2. 조회 목적별 SQL·인덱스 개선

- 근거: `examinees.repository.ts:104`의 출력 완료 집계 파생 테이블은 교시/수험생 조건을 내부에 명시하지 않는다. 단일 수험생 조회에도 공통 JOIN이 사용된다. 이를 단순화한 동일 조건 EXPLAIN에서 출력 집계에 `Using temporary; Using filesort`가 확인됐다. 현재 출력 이력은 14건뿐이므로 느리다는 실측 근거는 아니다. 실제 비용은 옵티마이저와 데이터 분포에 따라 달라진다.
- 개선: 단건 조회는 수험생 ID 기반 MAX/EXISTS, 명단은 해당 교시 ID 범위의 집계, 교시 카드만 전체 집계를 사용하도록 나눈다. 재출력·실패 기록이 총원을 부풀리지 않는 기존 의미를 유지한다.
- 실제 `candidate_record` 인덱스는 PK, 수험번호로 시작하는 복합 유일 키, 이름, 시험일이다. 전형·교시·고사실별 조회에 맞는 복합 인덱스를 검토할 여지가 있다. `print_job(candidate_record_id,status,sent_at)`은 이미 있으므로 중복 추가하지 않는다.
- 후보 인덱스는 `(admission, exam_date, start_time, period_name, status, id)` 등 실제 WHERE와 정렬을 기준으로 EXPLAIN 후 정한다. 긴 문자열의 키 길이와 쓰기 비용을 검토하고 비슷한 인덱스를 무작정 누적하지 않는다.
- 시스템 설정 목록은 이미 전형/설정/범위를 묶어 3회 조회하므로 전형마다 N+1 조회를 한다고 볼 수 없다. 다만 모든 카드에 전체 범위를 반환하며 저장 시 모든 범위를 UPSERT하므로, 규모가 커지면 카드용 집계와 편집 상세를 나누고 변경 범위만 저장한다.

### P2-3. 긴 등록·내보내기 작업의 백그라운드 처리

- 근거: 업로드 클라이언트는 5분 요청 제한으로 완료 응답을 기다린다. 별도 작업 ID·진행량·완료 상태 조회가 없다. `candidates.service.ts:228`과 `pseudonym-roster-exporter.ts:8`은 전체 행과 워크북을 메모리에 만든 후 writeBuffer한다. StreamableFile로 Buffer를 보내도 생성 단계가 스트리밍으로 바뀌지는 않는다.
- 개선: 큰 작업은 작업 ID를 먼저 반환하고 DB에 사용자·상태·처리량·결과를 보관한다. 초기에는 긴 작업 동시 실행 수를 작게 제한한다. 재연결 시 작업 결과를 조회하고 동일 등록 요청의 중복 반영을 막는다. 서버 재시작 후 미완료 작업을 무조건 재실행하지 않는다.
- 내보내기는 일정한 순서의 DB 묶음 조회와 ExcelJS streaming writer/임시 결과 파일을 조합한다. 임시 파일을 다운로드 스트림으로 제공하고 만료·실패 정리를 구현한다. 생성 중 데이터 변경 시 일관성 기준도 정해야 한다.
- 압축 해제·대량 파싱 등 CPU 작업은 별도 제한된 worker/process로 옮기는 것을 검토한다. async 함수나 Promise.all만으로 CPU 작업이 별도 스레드에서 실행되지는 않는다.

### P2-4. 편집 변경 시 전체 문서 정리·저장 빈도 조정

- 근거: `TemplateEditorWorkspace.tsx:174`의 onChange에서 전체 layout을 재귀 정리한다. `template-editor-serialization.ts:55` 이후 HTML DOM 파싱과 모든 요소 속성 정리를 수행한다. `FormTemplateManager.tsx:255`는 변경마다 전체 draft를 JSON으로 만들어 동기 sessionStorage에 기록한다.
- 개선: 편집기 내부의 실행 취소/트랜잭션은 그대로 두고 외부 draft 전달·임시 보관을 짧게 묶는다. 문서/페이지 revision 또는 마지막 처리 값으로 중복 정리를 생략하고, 저장·미리보기·편집 종료에서는 반드시 최신 내용을 동기 반영한다.
- 이 부분은 구조상 후보이며 실제 입력 프레임 지연은 아직 측정하지 않았다. 큰 표·여러 페이지·한글 조합 입력에서 지연을 먼저 계측한다. 9월 18일 ExamList 편집기 계측 변경이 현재 vendored `.21`에 반영됐다고 가정하지 않는다.

## 4. 이미 개선돼 있어 유지할 부분

- 대시보드는 SQL 집계만 반환한다. 수험생 목록의 전체 조회 문제와 다르다.
- 시스템 설정 목록과 계정-전형 연결은 묶음 조회+Map 조립을 사용한다.
- 현장 부여 후 해당 행 갱신, 오래된 교시 응답 차단, PDF 취소·제한된 사진 동시 요청이 구현돼 있다.
- 편집기와 PDF 라이브러리의 지연 로딩이 구현돼 있다.
- DB migration 적용 이력·체크섬·advisory lock, 변경 작업 트랜잭션·감사, 계정 session version, 출력 멱등성 검증은 성능 개선 중 유지해야 한다.
- 인증을 빨리 하려고 사용자 권한 검증을 긴 캐시에 넣거나, 번호 충돌을 막는 잠금을 검증 없이 제거하는 방식은 권장하지 않는다.

## 5. 실행·전송·검증 기반의 보완

1. **운영 빌드 실행**: 현재 `start-server.bat`은 `npm run dev`로 Vite와 tsx watch를 실행한다. 서비스 기반 운영 실행은 별도 제안대로 진행할 수 있다. 개발 모드의 요청 수·번들 동작을 운영 성능으로 혼동하지 않는다.
2. **전송 압축**: 현재 로컬 JSON 응답은 압축되지 않는다. 운영 웹 서버/API 경계에서 텍스트 압축을 적용하되 목록/상세 분리를 먼저 한다. 압축만으로 DB 조회·JSON 파싱 비용까지 줄어들지는 않는다.
3. **측정 지표**: 기존 HTTP duration/request ID에 DB 조회 수·반환 행·연결 획득 대기·트랜잭션/잠금 시간·응답 바이트·RSS·이벤트 루프 지연을 추가한다. 개인정보나 SQL 파라미터 원문은 남기지 않는다.
4. **E2E 준비 실패 처리**: `e2e/run.mjs:46`은 seed 프로세스 종료 코드를 확인하지 않고 다음 단계로 넘어간다. `e2e/seed.mjs:175`의 candidate INSERT는 현 스키마의 필수 `exam_name`, `label_barcode`를 넣지 않고, 뒤쪽에 정리 전 `examinee` 테이블 경로도 남아 있다. 실제 이전 화면 테스트 실행에서 `label_barcode` seed 실패 후 테스트가 계속되는 현상을 확인했다. 성능 회귀 검증 전에 seed를 현재 스키마에 맞추고 준비 실패 시 즉시 실패시키는 것이 필요하다. 이번 점검에서 전체 테스트를 다시 실행한 것은 아니다.
