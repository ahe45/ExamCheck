# 보안 기준 및 적용 상태

## 실행 구성 검증

API는 네트워크 포트와 DB 연결 설정을 사용하기 전에 단일 검증 함수로 정규화한다. `PORT`와
`DB_PORT`는 1~~65,535 정수, `DB_CONNECTION_LIMIT`는 1~~1,000 정수만 허용하며 잘못된 값이면
기본값으로 조용히 대체하지 않고 시작을 중단한다. `DB_NAME`은 영문자·숫자·밑줄만 허용한다.
서버 런타임과 migration/bootstrap 명령이 같은 DB 검증 함수를 사용하므로 실행 경로별 해석 차이가
없다. 로컬 기본값은 기존과 동일하게 API 3,100번 포트, DB 3,306번 포트, 연결 10개다.

운영 환경에서는 기본 개발용 JWT secret과 초기 계정 비밀번호 `1234`를 거부한다. 운영용
`JWT_SECRET`은 최소 32바이트의 난수를 base64url로 인코딩한 43자 이상의 값이어야 하며, 짧거나
반복 문자가 대부분인 저엔트로피 값도 시작 단계에서 거부한다. 초기 계정 bootstrap은 누락된
계정만 만들고 기존 계정의 비밀번호·권한·활성 상태는 덮어쓰지 않는다.

비밀번호는 난수 salt를 사용하는 scrypt로 저장한다. 로그인·계정 생성·비밀번호 변경·초기 계정
생성은 모두 비동기 `crypto.scrypt` 경로를 사용해 암호 계산 중 Node.js 이벤트 루프를 동기적으로
점유하지 않는다. 비밀번호나 파생 키는 로그와 감사 상세에 기록하지 않는다.

## 양식 HTML 보안 검사

양식 저장 API는 `layout` JSON 전체를 재귀적으로 검사한다. 실행 가능한 요소·이벤트 속성·위험한
URL 또는 CSS가 발견되면 원문이나 개인정보를 오류에 포함하지 않고 저장 요청을 거부한다. 저장된
양식을 미리보기·인쇄·PDF DOM에 넣기 전에는 DOMPurify allowlist를 다시 적용해 API 외 경로 또는
과거 데이터가 렌더링 경계를 우회하지 못하도록 이중으로 방어한다. 데이터 태그용 `data-*`, 표와
인쇄 레이아웃에 필요한 안전한 class·inline style은 유지한다.

검사 규칙은 다음 범주를 포함한다.

- `script`, `iframe`, `object`, `embed` 요소
- `meta http-equiv="refresh"`
- `on*` 이벤트 처리 속성
- `javascript:`, `vbscript:`, `data:text/html` URL
- CSS `expression()` 및 `url(javascript:...)`

정상 저장의 `FORM_TEMPLATE_SAVED` 감사 이벤트에는 검사 결과 `riskCount=0`만 기록한다. 거부 오류는
전체 위험 요소 개수만 안내하며 일치한 HTML, 속성값, 주변 문자열, 샘플 수험생 정보 등 원문이나
개인정보를 기록하지 않는다.

## 기존 양식 검토 게이트

신규 저장과 렌더링 차단은 적용되었지만, 기존 DB의 양식 원문을 자동 수정·삭제·비활성화하지는
않는다. 운영 전환 전 다음 절차로 기존 버전을 검토한다.

1. 운영에 등록된 모든 기존 양식 버전을 읽기 전용 검사해 규칙별 발생 원인을 검토한다.
2. 실제 정상 양식 fixture의 오탐이 0건이고 악성 fixture가 모든 규칙을 탐지하는 회귀 테스트를 유지한다.
3. 허용할 HTML 요소·속성·URL scheme·CSS 속성의 allowlist를 문서화하고 양식 편집기 및 PDF
   렌더러 양쪽에서 동일하게 검증한다.
4. 데이터 태그용 `data-*`, 표·인쇄 레이아웃용 인라인 스타일 등 업무상 필요한 항목이 allowlist에서
   손실되지 않는지 실제 양식으로 미리보기와 PDF 결과를 비교한다.
5. 기존 위험 양식의 수정, 비활성화 또는 격리 방안과 운영자 안내 절차를 마련한다.
6. 오탐이 발생했을 때 승인된 양식을 안전하게 변환하거나 예외를 추가하는 변경·검수 절차를 마련한다.
7. HTML 정리기를 도입하는 경우 정리 전 원문을 감사 로그에 남기지 않으며, 별도의 격리 저장이
   필요하면 개인정보 보관·암호화·접근 권한 정책을 먼저 승인받는다.

서버 deny-pattern과 브라우저 allowlist는 서로를 대체하지 않는다. 별도 창 인쇄와 PDF 렌더링은
동일 정리 함수를 사용하며, 운영 배포에서는 Content Security Policy도 별도로 적용해야 한다.

## 로그인 시도 보호

로그인은 정규화한 로그인 ID와 서버가 확인한 클라이언트 IP를 결합한 SHA-256 키로 실패 횟수를
관리한다. 기본값은 5분 안에 5회 실패하면 15분 차단이며, 임계값 도달 및 차단 중 요청에는 HTTP
429와 일반 안내 메시지를 반환한다. 성공하면 같은 키의 제한 상태를 초기화한다.

감사 로그에는 성공·실패·차단 이벤트와 `loginIdHash`, `ipHash`, `reason`만 기록한다. 비밀번호,
원문 로그인 ID, 원문 IP는 기록하지 않는다. 감사 저장 실패는 로그인 결과에 영향을 주지 않는다.

`AUTH_LOGIN_MAX_FAILURES`, `AUTH_LOGIN_FAILURE_WINDOW_SECONDS`, `AUTH_LOGIN_BLOCK_SECONDS`,
`AUTH_LOGIN_MAX_TRACKED_KEYS`는 누락되거나 공백이면 각각 `5`, `300`, `900`, `10000` 기본값을
사용한다. 값을 명시했다면 양의 정수여야 하며 `0`, 음수, 소수, 숫자가 아닌 값 또는 밀리초 변환
범위를 넘는 값은 기본값으로 대체하지 않고 서버 시작을 중단한다. 세부 동작과 운영 시 주의사항은
[로그인 시도 보호와 감사 로그](./auth-login-protection.md)에 정리한다.

현재 제한 상태는 API 프로세스 메모리에 있으므로 재시작하면 초기화되고, 여러 API 인스턴스
사이에서 공유되지 않는다. 다중 인스턴스 운영 전에는 Redis 등 원자적 만료를 지원하는 공유
저장소로 교체해야 한다. 역방향 프록시를 사용하는 경우 신뢰할 프록시 범위를 별도로 제한해야
하며, 그렇지 않으면 프록시 자체 IP 기준으로 제한될 수 있다.

## 세션 토큰과 강제 무효화

로그인 토큰은 기존과 같이 브라우저 `sessionStorage`에 저장하고 API 호출 시 `Authorization:
Bearer` 헤더로 전달한다. 토큰 헤더는 `alg=HS256`, `typ=JWT`만 허용하며, 본문의 사용자 ID·권한·
세션 버전과 함께 발급 시각(`iat`), 만료 시각(`exp`), 발급자(`iss`), 대상(`aud`)을 검증한다.
서버 시간 차이 허용 범위는 기본 30초이고 0~300초로 제한한다.

API는 보호된 요청마다 활성 계정의 현재 `session_version`과 권한을 다시 읽는다. 비밀번호 또는
권한이 변경되거나 계정이 비활성화되면 계정 변경 및 감사 로그와 같은 트랜잭션에서 세션 버전을
증가시킨다. 개발자 본인의 비밀번호 변경도 동일하다. 그 전에 발급된 토큰은 다음 요청부터
`로그인 정보가 만료되었습니다.` 응답으로 거부된다. 로그인 ID만 변경할 때는 세션을 유지하며,
전형 배정은 요청마다 현재 DB 값을 다시 조회하므로 별도 토큰 무효화 없이 즉시 반영된다.

`JWT_SESSION_TTL_SECONDS`는 양의 정수여야 하며 기본값은 28,800초(8시간)다. `JWT_ISSUER`와
`JWT_AUDIENCE`의 기본값은 각각 `examcheck-api`, `examcheck-web`이고 모든 API 인스턴스에서
일치해야 한다. 배포 환경의 `JWT_SECRET` 교체는 모든 기존 세션을 즉시 무효화한다.

## 수험생 데이터·사진 업로드 제한

수험생 XLSX와 사진 ZIP은 미리보기 및 실제 반영 API가 각각 동일한 검증 함수를 사용한다.
파일명 확장자와 브라우저가 전달한 MIME 유형을 먼저 확인하지만 이를 파일 형식의 근거로
신뢰하지 않으며, 두 형식 모두 업로드 데이터의 ZIP `PK` 시그니처를 필수로 확인한다. XLSX는
그 후에도 ExcelJS가 정상 OOXML 통합 문서로 해석할 수 있어야 기존 헤더·행 검증으로 진행된다.

현재 업로드 제한은 다음과 같다.

- XLSX 업로드 원본: 최대 25MB, `.xlsx` 확장자
- XLSX ZIP 항목 수: 최대 1,000개
- XLSX 내부 개별 항목의 비압축 크기: 최대 50MB
- XLSX 전체 비압축 크기: 최대 100MB
- XLSX 개별 항목 및 전체 압축률: 최대 100:1
- XLSX 필수 OOXML 관계·통합 문서·워크시트 항목이 없으면 거부
- 사진 ZIP 업로드 원본: 최대 200MB, `.zip` 확장자
- ZIP 항목 수: 폴더를 포함해 최대 5,000개
- ZIP 내부 개별 파일의 비압축 크기: 최대 20MB
- ZIP 전체 비압축 크기: 최대 500MB
- ZIP 개별 항목 및 전체 압축률: 최대 100:1
- 비압축 크기가 0보다 큰데 압축 크기가 0으로 기록된 항목: 압축 정보 오류로 거부
- 사진 가로·세로: 각각 최대 12,000픽셀
- 사진 전체 픽셀 수: 최대 40,000,000픽셀

ZIP 항목명에 절대 경로, Windows 드라이브 경로, `..` 경로 이동, 널 바이트가 하나라도 있으면
해당 파일만 건너뛰지 않고 압축 파일 전체를 거부한다. 이 정책은 현재 파일을 디스크에 풀지 않는
구현에서도 향후 추출 방식 변경 시 경로 이동 취약점이 생기지 않도록 유지한다. 항목 수·용량·압축률
한도를 넘거나 압축 정보가 모순되는 경우에도 압축 해제 전에 전체 업로드를 거부한다.

사진 후보 항목은 `.jpg`, `.jpeg`, `.png` 확장자와 실제 JPEG 또는 PNG 바이트 시그니처가 서로
일치해야 한다. PNG IHDR 또는 JPEG SOF에서 해상도를 확인하며, 헤더를 읽을 수 없거나 위 해상도
한도를 넘는 파일은 반영하지 않는다. 사진이 아닌 확장자, 이미지로 위장한 항목, 수험번호와 연결되지 않는 파일은 기존
응답 형식을 유지하기 위해 `skippedCount`에 포함해 건너뛴다. 반면 안전하지 않은 경로와 ZIP bomb
징후는 일부 반영하지 않고 전체 요청을 거부한다. 오류 응답은 항목명, 파일 내용, 압축 라이브러리의
원문 오류를 포함하지 않는 사용자 안내 문구만 반환한다.

미리보기 성공 응답에는 30분 동안 유효한 HMAC 서명 티켓이 `previewToken`으로 포함된다. 티켓은
업로드 종류, 인증 사용자 ID(actor), 파일 SHA-256, 현재 수험생 또는 사진 상태의 keyed checksum,
만료 시각을 묶는다. XLSX 상태 checksum에는 당시 수험번호 유일 정책도 포함한다. 상태 checksum을
계산할 때 현재 DB snapshot을 입력으로 사용하지만, 티켓에는 HMAC 결과만 넣어 수험생 필드·사진
상태의 원문 snapshot을 포함하지 않는다. 티켓과 checksum을 요청 로그나 감사 상세에 기록하지
않는다.

실제 반영 요청은 티켓을 query string으로 보내지 않고 `X-Candidate-Preview-Token` 전용 헤더로
전달한다. 서버는 1~2,048자이며 앞뒤 공백이 없는 문자열인지 먼저 확인한 뒤 HMAC 서명, 업로드 종류,
인증 actor, 파일 SHA-256, 30분 TTL을 검증한다. 이어서 transaction에서 관련 후보 행을 잠근 뒤
현재 상태 checksum을 다시 계산한다. 파일·사용자·데이터·유일 정책이 바뀌었거나 티켓이 만료되면
쓰기와 감사 기록 전에 전체 요청을 거부하고 새 미리보기를 요구한다. 이 티켓은 권한 검사를
대체하지 않으며 기존 인증·permission·전형 범위 검증도 그대로 적용된다.

미리보기의 `신규/수정/동일` 수치는 처리 정책과 무관한 원시 비교 결과다. 사용자는 이 분류를 본 뒤
신규만, 신규+수정, 전체 반영 정책을 선택할 수 있으며, 서버는 commit 시 잠근 동일 snapshot에서
선택 정책으로 실행 계획을 다시 만든다. 브라우저는 미리보기·반영 중 파일 입력과 정책 전환을
비활성화한다. 서명 티켓은 장기 보관·재개 가능한 staging batch를 대체하지 않으므로 대용량 비동기
import가 필요해지면 별도 batch 저장소와 수명주기를 도입한다.

## 인쇄 요청 멱등성과 재사용 차단

라벨 출력 요청은 사용자별 중복 방지 키와 함께 정규화한 수험번호·전형·날짜·시간·교시·
워크스테이션·매수를 SHA-256 지문으로 저장한다. 같은 사용자가 같은 키와 같은 요청을 재전송하면
기존 작업을 반환하지만, 필드가 하나라도 다르거나 지문이 없는 과거 작업이면 HTTP 409로 거부해
이전 수험생의 ZPL payload가 다른 요청에 재사용되지 않도록 한다. 동시 INSERT 고유키 경합 뒤의
재조회 경로에도 같은 지문 검사를 적용한다.

라벨 출력 작업 생성 API는 화면 표시 여부를 신뢰하지 않는다. 요청한 수험생의 정확한 일정과 전형
설정을 다시 조회하고, 가번호 부여 방식이 `PREASSIGNED`이면서 라벨 출력 사용이 켜진 경우에만
작업을 생성한다. 워크스테이션은 활성 등록 코드만 허용하며 생성과 감사 기록을 하나의 트랜잭션에
저장한다. 클라이언트 코드는 `VITE_WORKSTATION_CODE`로 주입하고 개발 호환 기본값만
