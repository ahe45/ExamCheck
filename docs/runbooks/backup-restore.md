# 개인정보 포함 DB 백업·복원 리허설 실행서

> 상태: 실행 전 템플릿  
> 적용 범위: 가번호 관리 시스템 MariaDB 11.4 계열  
> 주의: 이 문서는 절차와 증거 항목만 정의한다. 승인된 보관 위치와 개인정보 처리 정책이 없으므로 현재 백업·복사는 수행하지 않았다.

## 1. 실행 전 승인

아래 항목이 모두 기록되기 전에는 운영 또는 운영 복제 DB의 백업을 만들지 않는다.

| 항목                    | 기록값 |
| ----------------------- | ------ |
| 변경/리허설 ID          | 미정   |
| 실행 책임자             | 미정   |
| 개인정보·보안 승인자    | 미정   |
| 운영 승인자             | 미정   |
| 원본 DB 식별자          | 미정   |
| 격리 복원 환경 식별자   | 미정   |
| 암호화된 백업 보관 위치 | 미정   |
| 접근 가능 역할·계정     | 미정   |
| 보존 기간과 파기 일시   | 미정   |
| 허용 RPO / RTO          | 미정   |
| 작업 시간대             | 미정   |

승인 기록에는 백업 파일명이나 경로만 적지 않고 저장소 암호화, 전송 암호화, 접근 로그, 키 관리,
파기 방법과 사고 연락망을 함께 포함한다. 채팅, Git 저장소, 일반 공유 폴더, 로컬 임시 폴더는 승인된
보관 위치로 간주하지 않는다.

## 2. 사전 점검

1. 대상이 운영 DB인지 익명화 staging인지 명시한다.
2. 실행 계정에는 필요한 최소 read/backup 권한만 부여한다.
3. DB 제품·정확한 버전, charset/collation, timezone, SQL mode를 기록한다.
4. 현재 migration version과 checksum을 `docs/migration-manifest.md`와 대조한다.
5. 부분 적용 또는 checksum 불일치가 있으면 즉시 No-Go로 판정한다.
6. 사용 가능한 디스크 공간이 예상 백업 크기의 두 배 이상인지 확인한다.
7. 백업 시작·종료, 검증, 복원, 파기 이벤트를 기록할 변경 ID를 확정한다.

개인정보 원문, DB 비밀번호, 암호화 키, 전체 연결 문자열은 실행 로그와 증거 문서에 기록하지 않는다.

## 3. 백업 생성 원칙

- 운영 서비스가 계속 쓰는 동안에는 일관된 snapshot을 지원하는 방식만 사용한다.
- 스키마, 데이터, view, trigger, routine과 권한 포함 범위를 사전에 명시한다.
- 백업 산출물은 생성 즉시 승인된 키로 암호화하고 평문 임시 파일을 남기지 않는다.
- 산출물에는 변경 ID, DB 식별자의 비밀이 아닌 별칭, 시작 시각, 도구 버전을 연결한다.
- 파일 자체의 SHA-256은 별도 증거에 기록하되 파일 내용이나 개인정보 표본은 기록하지 않는다.
- 백업 성공 메시지만으로 완료 처리하지 않고 아래 복원 검증까지 수행한다.

실제 명령은 운영 플랫폼과 비밀 주입 방식을 승인한 뒤 변경 티켓에 첨부한다. 이 저장소에는 비밀번호가
포함된 명령, 연결 문자열 또는 운영 경로를 커밋하지 않는다.

## 4. 격리 복원 리허설

1. 운영과 네트워크·계정이 분리된 승인 환경을 준비한다.
2. 대상 DB 이름이 운영 DB와 다름을 두 번 확인하고 작업 기록에 남긴다.
3. 백업 checksum과 암호화 상태를 검증한 뒤 복원한다.
4. 애플리케이션 write를 연결하기 전에 read-only 검증을 먼저 수행한다.
5. 다음 항목을 원본의 비식별 집계와 비교한다.

   - migration version과 checksum
   - 테이블·view·trigger 수
   - 테이블별 행 수와 PK 최소/최대값
   - FK·unique·check 제약 수
   - 활성 계정 역할별 수와 세션 version 집계
   - 수험생·전형·교시·범위·할당·마감·양식·인쇄 작업의 비식별 건수
   - 최근 감사 이벤트 시각과 이벤트 유형별 건수

6. 애플리케이션 readiness와 read-only smoke를 실행한다.
7. 승인된 경우에만 migration rehearsal과 synthetic write/rollback 검증을 수행한다.
8. RTO와 실제 복원 소요 시간, 예상 RPO와 snapshot 시각을 비교한다.

원본 수험번호, 성명, 생년월일, 사진, 가번호는 리허설 보고서에 포함하지 않는다. 불일치 샘플이
필요하면 내부 숫자 ID와 salted digest만 사용한다.

## 5. 합격 기준

- 백업 checksum 검증 성공
- 복원 도구가 오류 없이 종료되고 migration checksum 일치
- 필수 schema object와 비식별 행 수가 승인된 허용치 안에서 일치
- FK·unique 무결성 검사 오류 0
- API readiness 성공과 역할별 read-only smoke 통과
- 승인 RTO 이내 복원 완료
- 평문 임시 파일과 사용 후 자격증명·임시 계정 잔존 0
- 증거 패키지와 파기 예정 시각 기록 완료

하나라도 실패하면 데이터 모델 expand, backfill, cutover를 시작하지 않는다.

## 6. 정리와 파기

1. 리허설 DB 접근을 차단하고 승인된 방식으로 DB와 임시 계정을 제거한다.
2. 백업 산출물은 승인된 보존 기간에 따라 유지하거나 파기한다.
3. 파기 결과에는 대상 별칭, 시각, 수행자, 검증 방법만 기록한다.
4. 로컬 작업 폴더, shell history, CI artifact, 브라우저 다운로드에 사본이 남지 않았는지 확인한다.
5. 사고 또는 잔존 사본이 발견되면 즉시 개인정보·운영 책임자에게 보고한다.
