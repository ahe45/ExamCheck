# 로그인 시도 보호와 감사 로그

## 동작

- 로그인 ID는 공백 제거, Unicode NFKC 정규화, 소문자 변환 후 사용한다.
- 정규화한 로그인 ID와 서버가 확인한 클라이언트 IP를 결합하고 SHA-256 해시한 값을 제한 키로 사용한다.
- 메모리에는 원문 로그인 ID나 원문 IP를 저장하지 않는다.
- 기본 정책은 같은 키에서 5분 동안 5회 실패하면 15분 동안 차단하는 sliding-window 방식이다.
- 임계값에 도달한 요청과 차단 중인 요청은 HTTP 429와 일반적인 안내 메시지를 반환한다.
- 정상 로그인에 성공하면 해당 키의 실패·차단 상태를 제거한다.

## 환경 변수

다음 값은 모두 초 단위 또는 횟수의 양의 정수만 허용한다. 누락되거나 공백이면 기본값을 적용하지만,
값을 명시한 경우 `0`, 음수, 소수, 숫자가 아닌 값 또는 안전한 정수 범위를 넘는 값이면 서버 시작을
거부한다.

| 변수                                |  기본값 | 의미                                    |
| ----------------------------------- | ------: | --------------------------------------- |
| `AUTH_LOGIN_MAX_FAILURES`           |     `5` | 제한 시간 안에 허용하는 실패 횟수       |
| `AUTH_LOGIN_FAILURE_WINDOW_SECONDS` |   `300` | 실패 횟수를 계산하는 sliding window     |
| `AUTH_LOGIN_BLOCK_SECONDS`          |   `900` | 임계값 도달 후 차단 시간                |
| `AUTH_LOGIN_MAX_TRACKED_KEYS`       | `10000` | 프로세스가 메모리에 보관할 식별 키 상한 |

세션 토큰 설정은 다음과 같다. TTL을 명시했다면 양의 정수가 아니면 서버 시작을 거부하고, 시간 차이
허용 범위는 0~300초 정수만 허용한다.

| 변수                          | 기본값          | 의미                         |
| ----------------------------- | --------------- | ---------------------------- |
| `JWT_SESSION_TTL_SECONDS`     | `28800`         | 로그인 토큰 유효 기간(초)    |
| `JWT_ISSUER`                  | `examcheck-api` | 토큰 발급자                  |
| `JWT_AUDIENCE`                | `examcheck-web` | 토큰 대상                    |
| `JWT_CLOCK_TOLERANCE_SECONDS` | `30`            | 서버 시간 차이 허용 범위(초) |

토큰에는 사용자 ID, 권한, 세션 버전, 발급·만료 시각, 발급자와 대상이 포함된다. 비밀번호·권한 변경,
계정 비활성화 또는 개발자 비밀번호 변경 시 DB의 세션 버전을 원자적으로 증가시켜 기존 토큰을 다음
요청부터 거부한다. 로그인 ID만 바꿀 때는 현재 세션을 유지한다.

## 감사 정보와 개인정보 경계

로그인 성공, 실패, 차단은 각각 `AUTH_LOGIN_SUCCEEDED`, `AUTH_LOGIN_FAILED`, `AUTH_LOGIN_BLOCKED`로 기록한다. `details` JSON에는 `loginIdHash`, `ipHash`, `reason`만 저장한다. 비밀번호, 원문 IP, 원문 로그인 ID는 저장하지 않는다. 조회된 사용자 행이 있으면 `actor_user_id`를 사용할 수 있지만, 존재하지 않는 로그인 ID는 원문이나 별도 식별 정보로 기록하지 않는다.

추적 키는 메모리 사용량이 입력값 수에 비례해 무한히 증가하지 않도록 상한을 둔다. 상한에 도달하면 만료되었거나 차단되지 않은 오래된 항목부터 정리한다. 이 제한기는 단일 API 프로세스의 방어선이므로, 다중 인스턴스 운영에서는 로드밸런서 또는 공유 저장소 기반 제한을 함께 적용해야 한다.

감사 로그 저장 실패는 일반 로그인 결과를 바꾸지 않는다. 저장 실패 자체도 원문 식별자나 데이터베이스 오류 전문을 로그에 출력하지 않는다.

## 운영 한계

현재 limiter는 API 프로세스 메모리에 있다. 따라서 서버 재시작 시 제한 상태가 초기화되며, API를 여러 인스턴스로 운영하면 인스턴스마다 실패 횟수가 따로 계산된다. 다중 인스턴스 운영 전에는 Redis 같은 공유 저장소와 원자적 만료 연산을 사용하는 구현으로 교체해야 한다.

클라이언트 식별자는 Nest/Express가 해석한 IP를 사용한다. 역방향 프록시 환경에서는 신뢰할 프록시 범위를 명시적으로 설정하고 전달 헤더를 외부에서 직접 주입하지 못하게 해야 한다. 프록시 신뢰 설정이 없으면 프록시 자체 IP 기준으로 제한될 수 있다.
