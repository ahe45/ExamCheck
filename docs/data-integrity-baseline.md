전체 할당 11건 중 6건은 migration 019~021을 거쳐 정확히 하나의 `candidate_record` 일정과 연결되었다. 나머지 5건은 모두 `admission_name = ''`인 기존 호환 데이터이며 일정 후보가 없거나 하나로 확정되지 않아 레거시 admission 범위 할당으로 보존했다. 자동 삭제하지 않는다. 해당 데이터가 필요한 운영 이력인지, 초기 sample/fixture인지 업무 담당자가 확인한 뒤 보존·이관·삭제 정책을 결정해야 한다.

활성 `examinee` 8건도 현재 업로드 데이터와 연결되지 않는다. 기존 migration sample 또는 구형 운영 흐름에서 생성된 데이터일 가능성이 있으나, 원문 식별자를 이 문서에 기록하지 않았으며 자동 정리하지 않았다.

## 가번호 범위 구조

- 전형 설정: `2026년도 자격시험 / 학생부교과 면접`
- 일정 범위: 6개
- 모든 일정의 시작 번호: `1001`
- 종료 번호: 최소 `1015`, 최대 `1039`
- 서로 겹치는 일정 범위 쌍: 15개

6개 범위의 모든 조합이 겹친다. migration 019~021 이후 가번호 고유키는 `시험명 + 전형명 + 유일 범위 key + 가번호`이며, 정확히 연결된 할당에는 `candidate_record_id`와 결정적 일정 scope key를 기록할 수 있다. 기본 정책 `ADMISSION`에서는 scope key가 비어 있어 전형 전체에서 번호가 유일하고, `SCHEDULE`에서는 교시별 scope key로 같은 번호를 다른 일정에서 재사용할 수 있다.

현재 데이터에는 복수 일정에 속한 동일 수험생이 0명이지만, 두 유일 정책의 동작과 더 좁은 정책으로 되돌릴 때의 충돌 차단은 별도 MariaDB fixture로 검증했다.

## 확정된 번호 유일 정책

- 수험번호: `SYSTEM`(모든 전형·날짜·교시에서 한 번만 사용) 또는 `SCHEDULE`(서로 다른 교시에서 재사용)
- 가번호: `ADMISSION`(전형 전체에서 유일) 또는 `SCHEDULE`(서로 다른 교시에서 재사용)
- 스키마와 설정의 기본값: 수험번호 `SYSTEM`, 가번호 `ADMISSION`
- 개발자 메뉴에서 변경하며, 현재 데이터가 더 좁은 정책과 충돌하면 원문 번호를 노출하지 않고 충돌 건수와 함께 저장을 거부한다.

Migration 019는 기존 `candidate_record`에 이미 동일 수험번호의 복수 일정이 있으면 적용 실패 대신 수험번호 정책을 `SCHEDULE`로 초기화한다. 충돌을 정리한 뒤에만 개발자 메뉴에서 `SYSTEM`으로 축소할 수 있다.

## 결정 전 금지 사항

- 기존 빈 전형 할당 5건 자동 삭제
- 업로드 데이터와 연결되지 않는 `examinee` 8건 자동 삭제
- 검증을 우회한 유일 정책 컬럼 직접 변경
- 전형 전체 연속 범위를 강제하는 설정 변경
- 정확한 일정 연결이 없는 레거시 할당에 임의의 `candidate_record_id` 지정

## 필요한 업무 결정

1. 기존 `admission_name = ''` 할당은 운영 이력인가, 삭제 가능한 sample인가?
2. 업로드 재실행 시 기존 가번호 이력을 유지해야 하는가?
3. 전형 전체 유일 방식이면 일정별 범위를 자동으로 연속 배치할 것인가?
4. 현재 `candidate_record` 기반 일정 identity를 독립 `schedule/registration` 모델로 언제 전환할 것인가?

번호 유일 정책과 최소 expand migration은 적용됐지만 이것은 RF-033/P0-4의 좁은 슬라이스다. 향후 독립 `schedule_id`, 공통 identity, dual-write·shadow 비교와 전체 Phase 5 cutover를 별도로 설계·검증한다.
